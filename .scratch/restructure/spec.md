# EduMind 模块化重构与前端重定制

Status: ready-for-agent

## 问题陈述

教师用户面对一个功能完整但难以日常使用的产品:所有功能挤在一个单文件界面的标签页里,知识管理、备课对话、冲突审核互相挤压;备课历史只存在浏览器里,清一次缓存全部丢失,换台电脑就断档;每次对话后端都从头重新理解全部需求,跳过追问靠硬编码关键词,改一处牵全身。维护者面对的是:模型名写死换不了、PDF 解析兜底逻辑焊死在类里、检索逻辑一半住在编排器里、接口没有专业文档、任何 AI 协作者进仓库都不知道规矩——项目无法持续演进。

## 方案

一次模块化重构:前端重写为**六区工作台**(会话/知识库/产物/知识图谱/冲突审核/题库 + 设置),以极简扁平硬标准(Minimalist Flat)定制界面与交互;后端成为**唯一事实源**(会话与生成物全版本持久化、对话状态机收编、意图增量累积),全部云端能力走**统一注册**(接口+实现+配置选择+stub 兜底,LLM 统一 OpenAI 兼容方言),新增设置界面让换供应商/换模型像 pi/opencode 一样即填即用;接口文档以 OpenAPI 为唯一事实源永不漂移,仓库自带分层规范(AGENTS/风格/ADR/词汇表)供任何 agent 与协作者遵守。

## 用户故事

**备课会话**

1. 作为教师,我想在一个以会话为中心的工作台发起备课对话,以便日常备课有稳定的主线入口。
2. 作为教师,我想发起会话时从知识库勾选参考资料,以便系统用我这批资料备课并在生成物中溯源。
3. 作为教师,我想在会话中直接上传文件并自动归入该会话的参考资料,以便边聊边补资料。
4. 作为教师,我想调整追问粒度(快速/标准/精细),以便控制澄清的强度。
5. 作为教师,我想用「开始生成」这类说法跳过追问,以便信息够用就直出生成物。
6. 作为教师,我想在多台设备看到同一份备课会话列表,以便办公室和家里接力备课。
7. 作为教师,我想清掉浏览器数据后备课历史依然完好,以便不怕误清丢失。
8. 作为教师,我想检索、重命名、删除会话,以便管理长期积累的备课记录。

**生成物**

9. 作为教师,我想生成后在对话旁并排看到课件、教案、提纲,以便立刻核对。
10. 作为教师,我想对单个生成物提修改意见再生成,以便局部调整不推翻全局。
11. 作为教师,我想查看某次会话的全部生成物历史版本,以便找回上一版更好的课件。
12. 作为教师,我想下载任意历史版本,以便直接用于课堂。
13. 作为教师,我想以某个历史版本为基线继续修改,以便从最好的那版出发迭代。
14. 作为教师,我想一键生成试卷且题目自动入题库并标注考查知识点,以便沉淀可复用题目。
15. 作为教师,我想按意图生成互动内容(单文件 HTML5)并在新标签页打开,以便课堂直接试用。

**知识库与图谱**

16. 作为教师,我想上传 PDF/Word/PPT/图片/视频/录音,以便沉淀个人教学资料。
17. 作为教师,我想看到文档解析状态(处理中/已完成/失败),以便知道什么时候可用。
18. 作为教师,我想把文档标记为参考资料,以便备课检索加权与溯源。
19. 作为教师,我想在图谱页以可视化形式查看知识图谱,以便直观把握知识点结构。
20. 作为教师,我想按学科/章节过滤图谱,以便资料多了也不糊成一团。
21. 作为教师,我想点击知识点节点查看详情(内容/难度/来源),以便核查提取是否准确。
22. 作为教师,我想从某个节点展开邻域子图,以便看清一个知识的上下游。

**冲突审核与题库**

23. 作为教师,我想在冲突队列里看到新旧知识对照卡片,以便判断定义冲突谁对。
24. 作为教师,我想对结构冲突看到「图谱现状 vs 三种裁决终态」的图示,以便明白每个按钮按下后图谱会变成什么样。
25. 作为教师,我想对常识存疑内容选择照常入库或拒绝,并可编辑修正后入库,以便可疑内容不污染知识库。
26. 作为教师,我想浏览题库并按考查知识点筛选,以便复习与组卷时取用。

**设置**

27. 作为配置者,我想在设置页从供应商目录选择并粘贴 API Key,以便像 pi/opencode 一样即填即用。
28. 作为配置者,我想按任务(意图分析/生成/冲突比对)选不同档位的模型,以便便宜任务用便宜模型、关键任务用强模型。
29. 作为配置者,我想添加自定义 OpenAI 兼容服务(base_url + 模型 ID),以便接入任何兼容网关。
30. 作为配置者,我想改完设置立即生效、Key 回读只见掩码,以便安全放心。
31. 作为教师,我想无 Key 时全功能可跑(stub 模式),以便先试用再决定接哪家云。

**维护者与协作者**

32. 作为维护者,我想换任何云端能力只改配置不改代码,以便对实现不满意时低成本替换。
33. 作为维护者,我想让检索与分块策略可插拔,以便升级 RAG 逻辑不动引擎躯干。
34. 作为维护者,我想接口文档与代码永远同步(OpenAPI 单一事实源),以便前后端与 agent 协作不靠人肉对齐。
35. 作为维护者,我想仓库自带分层规范(AGENTS/风格/ADR/词汇表),以便任何协作者按规矩工作。
36. 作为 AI 编码代理,我想进入仓库即知硬规则与验收标准,以便改动一次到位不返工。

## 实现决策

- **后端唯一事实源**:新增备课会话与生成物(全版本留痕)持久层;对话状态机(澄清→检索→生成→反馈)收进 core 层,api 路由只做参数校验与转发;意图按会话增量累积,替代每轮全量重析;跳过追问不再依赖硬编码子串词表。单用户模型不变。(ADR-0002)
- **能力注册**:每个外部能力 = 抽象接口 + 实现 + 配置按名选择 + 必有 stub。清单:LLM 对话(单一 OpenAI 兼容 provider 覆盖 dashscope/deepseek/siliconflow)、Embedder(从 LLM 接口拆出)、ASR、PDF 解析(mineru / pypdf / mineru 失败退 pypdf 三策略)、网络搜索、RAG 检索(Retriever:纯向量 / 向量+图谱融合两实现)、分块。向量存储不抽象。(ADR-0003)
- **模型配置**:全局默认 + 任务级覆盖(意图分析/生成/冲突比对三档起步);设置存储 + 设置 API 支撑设置界面,写穿即时生效、回读脱敏;`.env` 保留为引导默认。
- **RAG 策略收编**:检索逻辑从编排器移入 Retriever 实现,行为默认不变;重排留扩展位。
- **冲突数据模型**:Conflict 增加 category(定义冲突/结构冲突/常识存疑);差异化审核动作(定义与结构=三选一;常识存疑=两选一+编辑修正后入库);两类新类别的检测逻辑是重构后的独立功能槽,本轮只落数据模型。(ADR-0001/0004)
- **前端骨架**:六区(会话默认路由/知识库/产物/图谱/冲突/题库)+ 设置;四区为「二级侧栏列表+主区详情」,图谱与冲突主区直铺;URL 即路由。技术栈 Tailwind + Radix 无头原语 + 自建约 15 个扁平组件,react-router + TanStack Query(服务端状态)+ zustand(UI 状态);API 类型由 OpenAPI schema 生成,禁止手抄。(ADR-0005)
- **视觉硬标准**:Minimalist Flat——黑白 + 唯一强调色 #ff3366(强调色上只放黑字)、零阴影/零渐变/零灰底、border-2 border-black、rounded-none、悬停黑白反色、动效 ≤200ms 纯色彩变化;密度双轨(工作台密度=数据区,编辑密度=空状态/设置/引导);自托管 Noto Sans SC + Space Grotesk;mermaid 图谱按扁平主题定制,四种关系用黑/强调色的实线/虚线区分。验收清单见风格文档。
- **会话与文档绑定**:发起会话勾选参考资料,会话内上传自动归入;检索加权、生成物溯源沿用现有机制升级。
- **接口文档**:OpenAPI 唯一事实源,每端点必带 summary/描述/示例/错误码/tag;Swagger UI 与 ReDoc 双界面;机器表达不了的语义专题另立文档;破坏性变更才升 v2。
- **API 契约自由重设计**:唯一消费者是重写中的前端,不留兼容包袱。
- **落地策略**:前端新骨架一次成型;后端增量(持久层+能力层先行,再逐路由切换);主干任一时刻可跑;旧 localStorage 会话自然废弃不迁移;README 口径同步修订。

## 测试决策

- **单一主缝:HTTP API**。沿用仓库既有模式(FastAPI TestClient + stub 能力 + conftest 临时 SQLite 隔离),零新缝。好测试只断言外部行为——API 响应、状态变迁、落盘产物与数据,不断言内部函数调用与实现细节。
- **主缝覆盖点**:对话状态机(澄清/跳过/意图累积)、会话与生成物持久化(版本留痕、回看、以版本为基续改)、能力配置选择(stub 模式全链路可跑为底线测试)、冲突三类别数据模型与差异化审核动作、两种检索策略的行为差异、设置 API 的即写即生效与回读脱敏。
- **云端契约测试**:沿用 httpx MockTransport 模式单测 provider 契约(OpenAI 兼容方言切换后同样适用)。
- **前端**:不建组件测试缝;新增禁用类扫描脚本(正则扫禁用 class 清单,挂入 lint/build)作为风格守门工具,非测试缝。
- **先例**:现有 API 缝测试(test_chat/test_documents/test_conflict 等)、conftest 临时库隔离、test_audio 的「API 缝 + stub + MockTransport」三位一体模式,全部延续。

## 范围外

- 多用户与登录体系(单用户 user_id="default" 不变)
- 移动端/平板适配(桌面浏览器优先)
- 向量存储抽象(单实现,无更换动机)
- 外部插件包注册机制
- 结构冲突与常识存疑的**检测逻辑本体**(仅落数据模型,检测为后续功能槽)
- 旧 localStorage 会话的迁移
- 组件测试/端到端测试基建

## 进一步说明

- 决策依据全部固化于 `docs/adr/0002`–`0005` 与 `docs/architecture.md`,实现时遇取舍以 ADR 为准;ADR 冲突须显式提出,不得静默绕过。
- 面向教师的文案一律使用 `CONTEXT.md` 词汇表术语(备课对话/生成物/追问粒度/冲突/三选一/参考资料/题库)。
- 前端交付以风格文档自检清单为 Definition of Done。
- 建议工单拆分顺序(to-tickets 可参考):后端持久层与能力注册 → 对话状态机收编 → 前端骨架与六区路由 → 各区功能 → 设置界面 → 冲突数据模型 → README/文档收尾。
