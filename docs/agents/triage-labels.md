# Triage labels：工单状态词汇

标签名即角色名，写在工单的 `**Status:**` 行。**一张票同一时刻只有一个标签**。

| 标签 | 含义 | 谁能标 | 下一步 |
| --- | --- | --- | --- |
| `needs-triage` | 刚记录下来，尚未判断该做什么、该谁做 | 维护者 | 判断 → 转 `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix` |
| `needs-info` | 缺关键信息，现在无法判断或无法验收 | 维护者 | 补齐信息（复现步骤、期望行为、验收标准、受影响范围）后重新分诊 |
| `ready-for-agent` | 需求与验收项齐备，AI 协作者可独立开工 | 维护者 / 协调者 | 开工；交付后由维护者复核 |
| `ready-for-human` | 需要只有人能完成的一步，agent 不得开工 | 维护者 | 人工处理（真实 Key、主观视觉判断、对外沟通、不可逆操作） |
| `wontfix` | 明确不做 | 维护者 | 保留工单与理由，不删除 |

## 判定要点

**进 `ready-for-agent` 的硬条件**（缺一不可）：

- `What to build` 说清了面向教师的行为变化；
- 每个验收项都可观测（可跑的命令 / 可断言的 API 行为 / 可逐项核对的清单）；
- `【Ownership】` 写明了可改路径与禁区；
- 依赖（`Blocked by`）都已关闭，或写明了「None」。

**什么必须留在 `ready-for-human`**：需要真实云端 Key 才能做的验证（无 Key 环境下 agent 只能走 stub）、
需要人眼判断的视觉效果、需要对外沟通或涉及仓库外资源的动作、任何不可逆操作。

**`wontfix` 的写法**：在工单正文里写明不做理由，并指向依据（`docs/adr/` 里的决策，或 `spec.md` 的「范围外」条款）。
保留工单本身，因为它记录了「曾经考虑过且决定不做」这一信息。

## 状态迁移

- 迁移由维护者 / 协调者执行；执行者只在 `## 交付记录` 里报告「做了什么、验到什么、剩什么」。
- 交付记录里的遗留问题若需要决策，维护者据此新建工单或改标签，**不把问题留成口头约定**。
- 依赖被 `wontfix` 的票，其下游票必须重新判断（调整验收项或一并 `wontfix`），不得默认照常开工。
