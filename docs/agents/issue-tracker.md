# Issue tracker：本仓库的工单怎么记

本仓库没有远端 issue tracker。工单是**仓库里的 markdown 文件**，与代码同分支演进。

## 目录结构

```text
.scratch/
└── <feature>/                    # 一批相关工单共用一个 feature 目录，如 restructure
    ├── spec.md                   # 这批工单的共同上下文（问题陈述 / 方案 / 用户故事 / 实现决策 / 测试决策 / 范围外）
    └── issues/
        ├── 01-<slug>.md
        ├── 02-<slug>.md
        └── ...
```

- `spec.md` 是**共同上下文**，工单里不重复它；工单只写「这一刀切在哪里」。
- 命名：`NN-<slug>.md`，`NN` 为两位序号（决定执行顺序），`<slug>` 用小写英文短横线。
- 序号与 `Blocked by` 共同定义依赖顺序；序号不保证可以并行。

## 工单格式（固定五节）

```markdown
# NN: 名称

**What to build:** 一段话说清这张票要交付什么（面向教师的行为变化，不是文件清单）。

**Blocked by:** None (can start immediately) 或 依赖的票号

**Status:** <triage 标签，见 docs/agents/triage-labels.md>

- [ ] 验收项（可观测）
- [ ] 验收项（可观测）
```

另外可带（按需）`【票】/【环境】/【工作流】/【本票要交付】/【约束】/【Ownership】/【可观测验收】/【收尾】`
等段落，由派发者补充。

## 工单纪律

1. **一张票一个可独立验收的纵切**。拒绝「顺便重构一下」这类无法验收的混合范围。
2. **验收项必须可观测**：能跑的命令、能点到的界面、能断言的响应或数据变迁。
   「代码更清晰」「结构更合理」不是验收项——写不出如何验证，就不要写进验收项。
3. **依赖用 `Blocked by` 指向票号**；被阻塞的票不得开工（不要「先把架子搭上」）。
4. **改动范围用 `【Ownership】` 写清**：可改路径与禁区并列。拿到票先读 ownership 再动手。
5. **交付即勾选**：完成时在票内勾选已达成项，并追加 `## 交付记录` 节，内容至少包含：
   分支、commit sha、跑过的命令与结果、新建 / 改动的文件清单、遗留问题。
   验收项没达成就**不勾选**，并在交付记录里写明原因——不得静默跳过。
6. **过程稿不入库**：`DESIGN.md` / `PLAN.md` / `proposal.md` / `paseo.json` 保留在本机
   `.git/info/exclude` 里，属于阶段性草稿，不作为决策来源。工单与 `spec.md` 入库。
7. **决策内容只能来自**：本批工单、`AGENTS.md`、`CONTEXT.md`、`docs/adr/`、现有代码。
   仓库外文档（含历史草稿的其它副本）不得引用为来源。

## 状态与标签

工单 `**Status:**` 行只有一个标签，取值与含义见 `docs/agents/triage-labels.md`。

- 派发者决定开工；执行者**不自行改 Status**，只在 `## 交付记录` 里报告结果与遗留。
- 标签由维护者或协调者按交付记录推进（例如 `ready-for-agent` → 交付 → 维护者复核后关闭）。

## 为什么是本地 markdown

- 单机单用户项目，工单与代码同分支同 commit 演进，`git log` 本身就是工单史。
- AI 协作者进仓库即能读到全部上下文，不需要远端 API、鉴权或跨系统同步。
- 代价：没有远端看板与通知；需要人来维护序号与依赖关系。
