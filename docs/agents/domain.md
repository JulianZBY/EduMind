# Domain docs：这个仓库的领域文档怎么维护

**单上下文（single-context）**：一份 `CONTEXT.md` + 一个 `docs/adr/`，都放在仓库根。没有多模块领域拆分。

## 文档地图

| 文件 | 回答什么问题 | 谁在读 |
| --- | --- | --- |
| `CONTEXT.md`（根） | 「这个词在教师嘴里是什么意思」——面向教师的领域词汇表 | 任何要写面向教师文案或命名的人（含 AI 协作者） |
| `docs/adr/` | 「当初为什么这么定」——有取舍的决策记录 | 想改既有行为的人 |
| `docs/architecture.md` | 「整体长什么样」——目标架构一页图 | 第一次进仓库的人 |
| `docs/style/minimalist-flat.md` | 「界面必须长什么样」——前端验收硬标准 | 所有前端改动 |
| `docs/api/` | 「OpenAPI 表达不了的协议语义」 | 读接口读不懂的人 |
| `docs/agents/` | 「工单与协作怎么走」 | 派发与执行的人（含 AI 协作者） |
| `AGENTS.md` / `backend/AGENTS.md` / `frontend/AGENTS.md` | 「动手前必须知道的铁律」 | 全部 |

指向关系：`AGENTS.md` 是入口，它指向上面每一份文档；本目录（`docs/agents/`）描述这些文档之间怎么配合。

## CONTEXT.md 的维护规则

1. **词汇表只有面向教师的术语**，不写实现细节、不写表名与函数名。判断标准：这句话能不能原样念给教师听。
2. **引入新的面向教师概念时，同一次改动里加词条**（概念与文案一起进，不留「名字后补」）。
3. **发现同一概念两种叫法，必须当次消解**：统一成词表里的那一个，并在交付记录里写明改了什么。
   不得静默留偏差——「生成物 / 产物」这类并存会一路传播到界面文案里。
4. 每个词条写清**是什么**与**边界**（易混词要说明为什么不是另一个词）。
5. 词条描述「当前行为」时以代码为准；描述「目标行为」时带票号，两者必须可区分。

## ADR 的维护规则

- **只记录有取舍的决策**：做这件事有代价、有替代方案、别人可能会问「为什么不那样做」。
  操作手册、实现步骤、字段清单都不进 ADR（那些进 `docs/` 的其它文档或代码注释）。
- 每份 ADR 四节固定：**背景 / 决策 / 后果 / 被否决的替代方案**，外加状态、日期与相关文档。
- 编号**单调递增、不复用**。推翻旧决策 = 新写一份 ADR，并在旧 ADR 顶部标注「被 ADR-xxxx 取代」；
  不改写历史记录。
- **与既有 ADR 冲突时必须显式提出**：在交付记录里指出冲突的是哪一份、为什么这次要偏离。
  静默绕过是明确禁止的行为（见根 `AGENTS.md`）。
- 决策来源只能是：本仓库的工单与 `spec.md`、三份 `AGENTS.md`、`CONTEXT.md`、既有 ADR、现有代码。
  仓库外的过程稿不得作为决策来源。

## docs/api/ 的边界

- 只放**机器表达不了的协议语义**：动作的领域含义、多步流程的顺序、跨端点的状态约定、错误语义的取舍。
- 端点清单、字段、类型、示例以 `/openapi.json` 为准。**冲突时以 OpenAPI 为准**，
  并当场修文档（不要两份都留着让人猜）。
- 新端点不需要在 `docs/api/` 里补一份镜像文档；只有当读接口仍读不懂语义时才写专题。

## 什么时候该动哪份文档

| 触发 | 动哪份 |
| --- | --- |
| 新增 / 改名面向教师的概念 | `CONTEXT.md`（必要时同步 `docs/style/minimalist-flat.md` 的文案规范） |
| 做了一个有替代方案的取舍 | `docs/adr/` 新增一份 |
| 整体结构变化（分层、六区、数据流） | `docs/architecture.md` |
| 视觉或交互标准变化 | `docs/style/minimalist-flat.md`（同步前端 `AGENTS.md` 的指针描述） |
| 协议语义变化 | 对应的 `docs/api/*.md` |
| 工单流程变化 | `docs/agents/issue-tracker.md` / `triage-labels.md` |
