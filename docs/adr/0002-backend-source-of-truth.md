# ADR-0002：后端是备课会话与生成物的唯一事实源

- 状态：已接受（票 01 固化）
- 日期：2026-09-24
- 相关：`docs/architecture.md`、ADR-0003、票 05（会话持久层 + 状态机收编）、票 07（生成物全版本留痕）

## 背景

重构前的实际状况：

- 备课历史只住在浏览器 `localStorage` 里。教师清一次浏览器数据就断档，换一台电脑从零开始。
- `POST /api/v1/chat` 完全无状态：请求带整段对话历史，后端每轮把全部需求重新分析一遍意图。
- 「跳过追问」由路由层硬编码的子串词表判断（`_SKIP_WORDS`），换一种说法就失效。
- 对话状态机（澄清 → 检索 → 生成 → 反馈）的流转逻辑散在路由层里，改一处牵全身。
- 生成物落盘为随机命名的文件，数据库里没有记录。「上次那版课件更好」在本实现里无处可取回。

这些现象是同一个根因：会话与生成物的事实源不在服务端，而在一次性的进程内存与浏览器里。

## 决策

- **事实源后移**：新增备课会话、会话消息、生成物三层持久化（SQLAlchemy 2 同步 + SQLite），
  备份与迁移只针对服务端库。单用户模型不变（`user_id="default"`），本决策不引入登录体系。
- **全版本留痕**：每次生成都落一条新版本记录，同一会话内版本号单调递增；旧版本可回看、可下载、
  **可作基线继续修改**——以历史版本为基线修改产出更高版本号的新版本，原版本保持可取。
  落盘文件与版本记录一一对应，可按版本取回正确文件。
- **状态机收编**：澄清、追问判断、检索、生成、反馈的流转收进 `core/` 层；`api/v1/` 只做参数校验与转发，
  路由层不再持有业务状态。澄清与追问的决策不再住在路由里。
- **意图增量累积**：意图按会话累积（上一轮意图 + 本轮新增），替代每轮全量重析全部对话。
- **跳过追问语义化**：「信息够用就直出生成物」改为语义判定，不再依赖硬编码子串词表。
- **旧数据不迁移**：`localStorage` 里的旧会话自然废弃，不写迁移器。

## 后果

正面：

- 换设备、清浏览器数据后备课历史不丢；前端降级为纯渲染层，浏览器里不再有事实源。
- 生成物的「找回上一版」成为一步操作，修改产生新版本而非覆盖旧版。
- 测试缝不变：仍是 HTTP API（`TestClient` + stub 能力 + conftest 临时 SQLite 隔离），
  好测试只断言响应与数据变迁，不断言内部函数调用。

代价与约束：

- 后端成为单点：库损坏即备课历史损坏，需要备份意识（SQLite 单文件，成本低）。
- 请求形状会变（会话 id 成为对话的载体），前端必须同步重写——见 ADR-0005 的「不留兼容包袱」。
- 建表与演进靠 `init_db()` 幂等建表（见 `app/db`），字段语义写进 `db/models.py` 注释。
- 铁律：状态机不得回流到路由层；`api/` 层不得持有业务状态。

## 被否决的替代方案

1. **继续用 `localStorage` + 手动导出/导入文件**作为跨设备手段。
   否决理由：这是把「多台设备看到同一份会话」的用户故事丢给教师手工完成，且导出文件本身没有版本语义。
2. **双写：前端缓存 + 后端库同时作为事实源**。
   否决理由：两个事实源等于没有事实源——两边不一致时没有任何机制裁决谁对，缓存失效与竞态要在前端手写一遍。
3. **每个会话一个 JSON 快照文件，不建关系表**。
   否决理由：拿不到会话列表检索、按会话分组的时间线、版本号单调递增这些查询；也无法与前端服务端状态缓存对齐。
4. **为旧 `localStorage` 会话写迁移器**。
   否决理由：旧结构不稳定，且唯一消费者是正在重写的前端；迁移成本与收益不成比例。
5. **生成物只保留最新一版，旧版随手清理**。
   否决理由：与「查看全部生成物历史版本」「下载任意历史版本」「以历史版本为基线继续修改」三条用户故事直接冲突。
