# ADR-0003：外部能力统一注册（接口 + 工厂 + 必有 stub）

- 状态：已接受（票 01 固化）
- 日期：2026-09-24
- 相关：ADR-0002、票 02（能力注册统一）、票 03（RAG 策略收编）、票 13（设置）、`docs/api/stub-mode.md`

## 背景

重构前外部能力散落各处，每一种都有自己的「换不掉」方式：

- **对话模型**一家一个类、一家一个分支（`core/llm/providers/` 下 dashscope 与 deepseek 各一份，
  工厂里 `if key == ...` 逐家判），模型名写在代码与提示词里，换供应商要动工厂与调用方。
- **向量化**挂在对话 provider 上（`LLMProvider.embed`），换对话模型会顺带换掉向量维度，
  进而要求重建整个向量库。
- **语音转写**有 stub 与 paraformer 两条路、有工厂，是仓库里唯一做对的样板。
- **PDF 解析**把「主路径失败就退本地 pypdf」的兜底焊死在解析类里（`PdfParser.parse` 的 `try/except`），
  想单独选 pypdf 或用别的服务没有入口。
- **网络搜索**只有写死的客户端（`BochaSearchClient`），没有接口、没有工厂、没有 stub，
  缺 Key 直接抛 `ValueError`。
- **向量存储**反过来是单实现（sqlite-vec），没有更换动机。

结论：缺的不是抽象能力，而是**统一的注册纪律**——「什么算一个能力、换实现要动哪里」在仓库里没有答案。

## 决策

- **每个外部能力 = 抽象接口（`base.py`）+ 实现 + 按配置选择的工厂（`factory.py`）+ 必有 stub**。
  新增实现无需改动调用方；调用方只认接口。
- **能力清单**（本轮确定为七项）：

  | 能力 | 接口位置 | 实现 | 配置项 |
  | --- | --- | --- | --- |
  | LLM 对话 | `core/llm/base.py` | OpenAI 兼容 provider（覆盖 dashscope / deepseek / 硅基流动）+ stub | `llm_provider` |
  | 向量化 Embedder | 从对话接口拆出 | 同上兼容实现 + stub | 随 provider 配置 |
  | 语音转写 ASR | `core/asr/base.py` | paraformer（阿里百炼）+ stub | `asr_provider` |
  | PDF 解析 | `knowledge/parsers/` + `core/parser/` | mineru / pypdf / mineru 失败退 pypdf 三策略 | 解析策略配置 |
  | 网络搜索 | 新增接口 + 工厂 | 博查（Bocha）+ stub | `bocha_api_key` |
  | RAG 检索 Retriever | `knowledge/` 策略接口 | 纯向量 / 向量 + 图谱融合 | 检索策略配置 |
  | 分块 Chunker | `knowledge/` 策略接口 | 现有分块 + 可插拔实现 | 分块策略配置 |

- **对话收敛为单一 OpenAI 兼容方言**：填 `base_url` + 模型 ID + Key 即可在 dashscope、deepseek、
  硅基流动之间切换，不再一家一个类。
- **Embedder 与对话拆开**：向量化是独立接口与工厂，调用方不再依赖对话 provider。
- **PDF 三策略**可经配置切换，原有「失败兜底」行为保留为其中一种策略而不是隐式行为。
- **配置优先级**：设置库（票 13）> `.env` 引导默认 > 代码默认。设置写穿后即时生效，回读只给掩码。
- **向量存储不抽象**：单实现、无更换动机，抽象只增加一层无收益的间接。
- **stub 模式是底线**：无 Key 时全链路必须可跑，破坏即阻塞。这也是「先试用再决定接哪家云」的前提。

## 后果

正面：

- 换供应商、换模型、换解析策略只改配置不改代码；不满意某个实现时替换成本可预估。
- 能力实现可单测：provider 契约用 httpx `MockTransport` 覆盖，三家方言各一例。
- RAG 策略（检索/分块）从编排器移进策略实现，编排器只消费结果，升级 RAG 逻辑不动引擎躯干。

代价与约束：

- **新增实现必须同时提供 stub**：成本上升是有意为之，用来保证无 Key 底线不被下一个人悄悄破坏。
- 能力选择是运行时状态，因此测试必须覆盖「按配置选择」本身；设置写穿要考虑实例缓存失效
  （现有 `get_llm()` / `get_transcriber()` 用 `lru_cache`，配置改变后必须能拿到新实例）。
- 一个兼容方言覆盖多家，各家的专有参数（推理开关、多模态字段差异）需要显式映射与契约测试兜住。
- 抽象边界要克制：向量存储这类单实现明确不抽象，避免抽象层比实现还长。

## 被否决的替代方案

1. **维持现状：一家一个 provider 类 + 工厂里的 if/else 分支**。
   否决理由：每加一家都要同时改工厂与所有调用方，且 embed 被绑在对话 provider 上，换模型会连带换向量维度。
2. **引入外部插件包注册机制（entry points / 可安装能力包）**。
   否决理由：单机单用户项目没有第三方分发需求，加载顺序、版本兼容、错误诊断的复杂度远大于收益（本项目范围外）。
3. **继续把 Embedder 挂在对话 provider 接口上**。
   否决理由：对话与向量化是两家、两套模型、两个计费口径；绑在一起会让「换对话模型」变成「重建向量库」。
4. **抽象向量存储**（为 sqlite-vec 再加一层接口）。
   否决理由：只有一个实现、没有任何更换动机，抽象层不带来可替换性，只带来阅读成本。
