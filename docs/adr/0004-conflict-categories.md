## 背景

仓库现有的冲突审核只有一个类别，代码与配置把它的检测与裁决标注为 ADR-0001
（该记录长期不在本工作树，票 01 只重建了 0002~0005，因此本文不重复其内容）。
**ADR-0001 已于 2026-09-25 找回并照录归档**（`docs/adr/0001-conflict-detection-convergence.md`）：
读「定义冲突的检测与三选一」去读它，读「当前的检测范围与两类暂缓项」去读 ADR-0006。
现有事实：

- `Conflict` 表只有 `status`，没有类别字段；`status` 取值 `待审 / 已接受 / 已拒绝 / 并存`。
- 检测只做**定义冲突**：同名精确匹配 + 标题向量近名预筛（阈值 `conflict_distance_threshold`），
  阈值内候选交 LLM 判断两段描述是否矛盾。
- 审核动作恒为**三选一**：接受新（替换旧节点并重挂边）/ 保留旧（丢弃新知）/ 并存（双节点保留）。
- `app/knowledge/conflict.py` 的模块说明明确写着「结构冲突、常识存疑不在承诺范围」。

三种冲突在教师眼里的形态完全不同，用一套动作与一种呈现装不下：

- 定义冲突是「同一个知识点，两种说法，谁对？」——需要新旧对照。
- 结构冲突是「新知识与图谱已有的层级/依赖关系打架」——需要看清裁决后图谱会变成什么样。
- 常识存疑是「这段内容可能是错的常识」——不是二选一谁对，而是「要不要让它进库」，且允许教师改对了再进。

## 决策

- **引入类别字段**：`Conflict.category` 取值 `定义冲突` / `结构冲突` / `常识存疑`；
  **存量冲突数据回填为 `定义冲突`**（现有检测只产出这一类）。
- **动作按类别差异化**：

  | 类别 | 动作集合 | 终态 |
  | --- | --- | --- |
  | 定义冲突 | 三选一 | `已接受` / `已拒绝` / `并存` |
  | 结构冲突 | 三选一 | `已接受` / `已拒绝` / `并存` |
  | 常识存疑 | 两选一 + 编辑修正后入库 | `已接受`（照常入库）/ `已拒绝`；修正入库时落库为**修正后内容** |

- **三选一语义不变**：接受新 = 新节点替换旧节点、旧节点的边重挂到新节点；保留旧 = 丢弃新知、图谱不动；
  并存 = 新旧双节点保留、差异说明留在冲突记录中。审核前新知不入图谱。
- **结构冲突必须可预览**：审核界面呈现「图谱现状 vs 三种裁决终态」的小型图示，复用知识图谱区的组件与扁平主题，
  让教师按下按钮前就知道图谱会变成什么样。
- **检测逻辑本体不在本轮**：结构冲突与常识存疑只落**数据模型与审核动作**，检测是重构后的独立功能槽。
- **文案不得超前**：README 与面向教师的文案不再承诺未实现的检测类别。

## 后果

正面：

- 三类冲突各有专属形态与动作，审核队列按类别分区呈现，教师不会面对「一个按钮问三件事」。
- 常识存疑有了「编辑修正后入库」这条出路，可疑内容既不用照单全收，也不用整段丢弃。
- 数据模型先落地，检测逻辑与前端呈现可以并行开发，互不阻塞。

代价与约束：

- 类别是**检测来源**的标记，不能靠动作反推：同一动作在不同类别下的含义不同（例如「并存」对常识错误没有意义）。
- 常识存疑的「编辑修正后入库」要求落库内容与原文可区分（原文留在冲突记录里，修正后内容才是入库内容），
  因此审核接口必须能接收并持久化修正后的内容。
- 回填是迁移的一部分；回填后有历史数据的库与新库行为一致（都从 `定义冲突` 开始）。
- 结构冲突的三种终态图必须与实际裁决后的图谱变化一致，否则比不给图更糟——这是验收项而非装饰。

## 被否决的替代方案

1. **三类各建一张表**。
   否决理由：审核队列是一个整体概念（分区呈现、统一裁决入口、统一计数），三张表会让队列查询与分区排序散成三份。
2. **只扩 `status` 枚举，不引入 `category`**。
   否决理由：`status` 会被迫同时表达「检测来源」与「裁决终态」两件事，动作集合也无法按类别收窄；
   且无法把「两选一 + 编辑修正」与「三选一」区分开。
3. **先实现全部检测逻辑，再补数据模型与审核动作**。
   否决理由：检测依赖提示词与阈值反复调优，会把前端呈现与审核动作一起拖住；先落模型能让两侧并行。
4. **常识存疑也用三选一**。
   否决理由：「并存」对常识错误没有语义——把一条错常识与正确内容并列保留，等于承认库里可以有错知识。
