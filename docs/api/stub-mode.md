# stub 模式：没有 Key 时的行为

**stub 模式 = 全链路可跑但没有真实云端能力**。它是本项目的底线：
无任何 Key 的机器上，从上传资料到备课对话到下载生成物必须能走通（票 14 的冒烟就是跑这条路）。

stub 模式不是「演示模式」，也不是「离线模式」：它照样落库、落盘、走完整状态机，
只是模型输出的**内容质量不作承诺**（stub 返回的是可解析的占位结果，用于验证链路与前端行为）。

## 各能力在无 Key 时的行为（重要：并不是全都一样）

| 能力 | 有 stub？ | 无 Key 时的行为 |
| --- | --- | --- |
| LLM 对话（`llm_provider=stub`，默认） | ✅ | 返回结构化占位结果，链路可跑 |
| 向量化（跟随 provider 配置） | ✅ | 返回兜底向量；可检索、可入库，但**排序不具语义意义** |
| 语音转写（`asr_provider=stub`，默认） | ✅ | 返回占位转写文本 |
| PDF 解析 | ✅ | pypdf 本地抽文本层天然不需要 Key；mineru 策略需要 `MINERU_TOKEN` |
| 网络搜索（`search_provider` 留空 = 自动档） | ✅ | 有 `BOCHA_API_KEY` 走博查，没有则回落 stub，返回带「（stub 网络搜索）」标记的占位结果 |

### 唯一一个「有 stub 但缺 Key 也会报错」的位置

网络搜索与其它能力有一个区别值得记住：**博查是真实实现，无 Key 时回落的是 stub 占位结果**，
而不是报错——结果文案里带「（stub 网络搜索）」标记，避免教师把占位内容当成教学依据。

但如果**显式**把 `search_provider` 配成 `bocha` 而 Key 缺失，就是 `500`（`detail` 为 `BOCHA_API_KEY 未配置`），
不静默回落到 stub。理由与下面「错误语义」一节一致：教师明确选了博查，就应该看到配置问题，
而不是收到一批看起来像真结果的占位内容。

## stub 模式下走不到的分支（演示前必读）

stub 让**链路**可跑，但不让**内容**可信，也不保证每个业务分支都能被触发。
下面三件东西在纯 stub 模式下走不到，演示时不要当成故障：

| 走不到的东西 | 原因 | 想看到它怎么办 |
| --- | --- | --- |
| **澄清回复**（追问粒度、跳过追问） | stub 的意图分析返回**固定且要素齐全**的意图（完整意图里没有任何缺失字段），因此每一轮对话都直接给生成回复；追问粒度与「跳过追问」判定不参与 | 真实模型下意图会因表述不全而缺失要素（见 `docs/acceptance-manual.md`）；自动化证据在 HTTP 缝用例：`uv run pytest tests/test_chat.py tests/test_session_turns.py -q`（用意图替身注入不完整意图） |
| **自然出现的冲突** | stub 的冲突比对恒返回「无矛盾」（`{"conflict": false}`），结构冲突与常识存疑的检测逻辑本身也尚未实现（ADR-0006） | 三类别与差异化裁决动作用**种子数据**验证：`uv run pytest tests/test_conflict_categories.py -q`；端到端跑法见 `docs/acceptance-manual.md` 的附录 |
| **真实的图谱 / 视觉提取内容** | 图谱提取回显正文前几行，视觉提取返回固定占位文本（票 15） | 接真实模型后才会基于实际上传内容产出 |

因此 stub 模式的定位是「链路联调 + 前端行为验证」，不是「内容验收」。

## 配置优先级

```text
设置页（票 13 交付）  >  .env 引导默认  >  代码默认值
```

- `.env` 是**引导默认**：第一次跑起来靠它，之后在设置页改过的值优先。
- 设置写穿后**即时生效、无需重启**；回读只给掩码，任何响应与表单都不回显明文。
- `llm_provider` 的默认值是 `stub`、`asr_provider` 的默认值也是 `stub`——
  即「什么都不配」时进入 stub 模式，而不是启动失败。

## 选择一个能力实现时的错误语义

配置指向一个**未实现的名字**（例如 `llm_provider=unknown`）时工厂立即抛错，服务不会静默回落到 stub：

- 配置指向真实实现但**缺 Key**（例如 `llm_provider=dashscope` 而 `DASHSCOPE_API_KEY` 为空）：
  同样抛错，不回落到 stub。
- 理由：静默回落会让「我明明配了 Key」变成「怎么结果还是假的」，症状比报错难查得多。

## 给前端与 AI 协作者的提醒

- 前端可以读 `GET /health` 的 `llm_provider` 字段得知当前是否 stub 模式，
  但**界面不需要把这个词暴露给教师**（「stub」是工程词，见 `CONTEXT.md` 的措辞纪律）。
- 写测试时默认就跑在 stub 模式下（conftest 隔离临时库 + 临时落盘目录）；
  需要真实网络的用例必须显式 mock（沿用 httpx `MockTransport` 契约测试模式），
  不允许测试依赖真实 Key。
