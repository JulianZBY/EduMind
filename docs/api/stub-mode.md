# stub 模式：没有 Key 时的行为

**stub 模式 = 全链路可跑但没有真实云端能力**。它是本项目的底线：
无任何 Key 的机器上，从上传资料到备课对话到下载生成物必须能走通（票 14 的冒烟就是跑这条路）。

stub 模式不是「演示模式」，也不是「离线模式」：它照样落库、落盘、走完整状态机，
只是模型输出的**内容质量不作承诺**（stub 返回的是可解析的占位结果，用于验证链路与前端行为）。

## 各能力在无 Key 时的行为（重要：并不是全都一样）

| 能力 | 有 stub？ | 无 Key 时的行为 |
| --- | --- | --- |
| LLM 对话（`llm_provider=stub`，默认） | ✅ | 返回结构化占位结果，链路可跑 |
| 向量化（跟随 provider 配置） | ✅ | 返回兜底向量；可检索、可入库，但**排序不具语义意义** |
| 语音转写（`asr_provider=stub`，默认） | ✅ | 返回占位转写文本 |
| PDF 解析 | ✅ | pypdf 本地抽文本层天然不需要 Key；mineru 策略需要 `MINERU_TOKEN` |
| **网络搜索** | ❌ | **无 stub**：`BOCHA_API_KEY` 未配置时请求失败（`500`，`detail` 为 `BOCHA_API_KEY 未配置`） |

最后一行是有意为之：网络搜索**不能**用占位结果糊过去——教师看到的是「搜到了什么」，
假结果会直接污染备课内容。宁可明确报错。

因此 stub 模式下的端到端冒烟**不包含网络搜索**；搜索相关的端到端验证需要一个真实 Key，
属于 `ready-for-human` 的范围（见 `docs/agents/triage-labels.md`）。

## 配置优先级

```text
设置页（票 13 交付）  >  .env 引导默认  >  代码默认值
```

- `.env` 是**引导默认**：第一次跑起来靠它，之后在设置页改过的值优先。
- 设置写穿后**即时生效、无需重启**；回读只给掩码，任何响应与表单都不回显明文。
- `llm_provider` 的默认值是 `stub`、`asr_provider` 的默认值也是 `stub`——
  即「什么都不配」时进入 stub 模式，而不是启动失败。

## 选择一个能力实现时的错误语义

配置指向一个**未实现的名字**（例如 `llm_provider=unknown`）时工厂立即抛错，服务不会静默回落到 stub：

- 配置指向真实实现但**缺 Key**（例如 `llm_provider=dashscope` 而 `DASHSCOPE_API_KEY` 为空）：
  同样抛错，不回落到 stub。
- 理由：静默回落会让「我明明配了 Key」变成「怎么结果还是假的」，症状比报错难查得多。

## 给前端与 AI 协作者的提醒

- 前端可以读 `GET /health` 的 `llm_provider` 字段得知当前是否 stub 模式，
  但**界面不需要把这个词暴露给教师**（「stub」是工程词，见 `CONTEXT.md` 的措辞纪律）。
- 写测试时默认就跑在 stub 模式下（conftest 隔离临时库 + 临时落盘目录）；
  需要真实网络的用例必须显式 mock（沿用 httpx `MockTransport` 契约测试模式），
  不允许测试依赖真实 Key。
