# 冲突裁决：动作语义与终态

端点：`GET /api/v1/conflicts`、`POST /api/v1/conflicts/{conflict_id}/review`。
字段与示例以 `/openapi.json` 为准；本文只解释 OpenAPI 表达不了的语义。

## 为什么需要本文

`action` 字段在 OpenAPI 里只是一个字符串枚举。它表达不了四件事：

1. 每种动作**对知识图谱做了什么**（教师的按钮按下去，图谱会变成什么样）；
2. 每条冲突只能裁决一次，重复提交为什么是 `409` 而不是 `400`；
3. 三类冲突的动作集合不同，其中「常识存疑」的第三条出路**不是三选一里的任何一项**，
   而且「动作不适用于该类别」与「已裁决」是两种不同的错误（`422` 与 `409`）；
4. 结构冲突为什么要多带一份 `structure_preview`——它是「图上承诺的终态」，不是装饰。

## 状态机

```text
        ┌──────────┐
        │  待审    │  ← 新知入库前停在这里，图谱里看不到它
        └────┬─────┘
   三选一/两选一 ┤
        ┌────┴───────┬──────────────┐
        ▼            ▼              ▼
    ┌────────┐  ┌────────┐    ┌────────┐
    │ 已接受 │  │ 已拒绝 │    │  并存  │
    └────────┘  └────────┘    └────────┘
```

- 只有 `待审` 状态的冲突可以被裁决；对已裁决的冲突再次提交动作返回 `409`
  （「已经处理过」是状态冲突，不是请求格式错误）。
- 裁决是**幂等边界**：一次请求要么完整生效，要么因 `404` / `409` / `422` 完全不生效。
- 审核前**新知不入知识图谱**——这是冲突检测的既定行为，也是「待审」存在的意义。

## 类别字段

每条冲突带 `category`：`定义冲突` / `结构冲突` / `常识存疑`（CONTEXT.md 第 6 节）。
类别是**检测来源**的标记，不能由裁决动作反推——同一动作在不同类别下含义不同。

| 类别 | 动作集合 | 终态 |
| --- | --- | --- |
| 定义冲突 | 三选一：`接受新` / `保留旧` / `并存` | `已接受` / `已拒绝` / `并存` |
| 结构冲突 | 三选一：`接受新` / `保留旧` / `并存` | `已接受` / `已拒绝` / `并存` |
| 常识存疑 | 两选一 + 编辑修正后入库：`照常入库` / `拒绝` / `编辑修正后入库` | `已接受` / `已拒绝` / `已接受` |

- 动作不在该类别的动作集合里 = `422`（与冲突当前状态无关的请求语义错误）；
  对已裁决的冲突再提交 = `409`。
- `GET /conflicts` 支持 `?category=` 与 `?status=` 两个独立过滤（都不传 = 全部）。

## 定义冲突与结构冲突：三选一

| 动作 | 对图谱做什么 | 终态 | 何时选它 |
| --- | --- | --- | --- |
| `接受新` | 新知识点替换旧知识点；旧知识点上原有的关系边**重挂**到新知识点；旧知识点删除 | `已接受` | 新描述更准确 |
| `保留旧` | 丢弃新知，图谱**不动**（新知从未入图，无需回滚） | `已拒绝` | 旧描述更准确，或新知表述有问题 |
| `并存` | 新旧两个知识点**都保留**，差异说明留在冲突记录中 | `并存` | 两种说法对应不同情境，都有价值 |

要点：

- 「接受新」会**移动边**而不是重建边：旧知识点作为起点的边与作为终点的边都会改挂到新知识点。
  因此选择「接受新」之后，图谱的拓扑与裁决前一致，只是那个位置换了一个节点。
- 「保留旧」不产生任何图谱变更，`conflict_count` 与文档状态也不因此变化——它记录的是**判断**，不是数据变更。
- 「并存」保留冲突记录里的 `diff_description`，教师日后能看到当初为什么两个都留。
- **结构冲突的新知可自带关系**（`new_knowledge["relations"]`，形如
  `{"from_title": ..., "to_title": ..., "relation": "推导关系"}`，端点按知识点标题解析）：
  随「接受新」/「并存」一并入图；端点在**被替换的旧节点**上时改挂到新知。
  「保留旧」不入图。

### 结构冲突的「图谱现状 vs 三种裁决终态」

待审的结构冲突在列表里多带 `structure_preview`：

- `current`：**图谱现状**——以冲突知识点为中心的**一跳邻域子图**（节点 + 关系）；
- `outcomes`：三种裁决终态各一张同形状的小图，外加该动作对应的 `status`。

三张终态图与实际裁决走的是**同一套语义**（接受新 = 新知顶替旧节点且旧节点的边改挂；
保留旧 = 不动；并存 = 双留 + 新知自带的关系入图），所以图上画的终态就是裁决后图谱的样子；
这条是验收项，不是装饰。新知在终态图里用占位 id `__new__`（真实 id 要等裁决后才生成），
并用 `is_new: true` 提示前端画强调色描边。

## 常识存疑：两选一 + 编辑修正后入库

| 动作 | 含义 | 终态 |
| --- | --- | --- |
| `照常入库` | 教师确认内容没问题，按原文进库 | `已接受` |
| `拒绝` | 不让它进库 | `已拒绝` |
| `编辑修正后入库` | 教师改对了再入库，**落库的是修正后的内容** | `已接受` |

与前两类的差别，正是 OpenAPI 表达不了的部分：

- 常识存疑问的不是「谁对」，而是「要不要让它进库」。因此**没有「并存」**：
  把一条可疑常识与正确内容并列保留等于承认库里可以有错知识。
- 「编辑修正后入库」必须能接收正文：请求体除动作外还要带 `revised_content`（缺了就是 `422`）；
  原文留在冲突记录的 `new_knowledge` 里，修正后的内容同时落在 `revised_content` 与图谱节点上，
  让「原来的说法」与「最终入库的说法」都可追溯。
- 落库内容以修正后的版本为准；原文只作为审核痕迹保留。
- 两条入库出路的终态都是 `已接受`，故记录里另存 `review_action`（教师实际选的动作）——
  只靠 `status` 分不出教师走的是哪条出路。

> 实现状态（ADR-0004 / ADR-0006）：类别字段与差异化审核动作已落地（票 11）。
> **检测逻辑只做定义冲突**：结构冲突与常识存疑的检测尚未实现，因此当前队列里只会出现定义冲突；
> 上表描述的是裁决动作契约，不是「现在就能看到的三类冲突」。
> 面向教师的文案与 README 不得承诺能自动发现另外两类。

## 存量数据

类别字段落地时，**存量冲突数据回填为「定义冲突」**：现有检测只产出这一类，
回填保证老库与新库的队列呈现一致，不产生「无类别」的中间状态。
回填与补列是同一条**幂等**迁移（`app/db/engine.py`），重复执行不会改变结果。

## 前端读法（避免踩坑）

- 裁决成功后请**重新拉取列表**（或按返回的 `id` + `status` 本地更新），
  不要乐观地把整条冲突从队列里删掉——`并存` 与 `已接受` 的呈现不同。
- 队列按 `category` 分区；`GET /conflicts?category=` 是过滤器，不是「只返回待审」的开关
  （那是 `?status=待审`）。
- `new_knowledge` 与 `existing_knowledge` 是**对照卡片**的两侧，不是「输入」与「上一版」；
  三者形态不同：定义冲突 = 新旧对照 + 三选一；结构冲突 = 再画「图谱现状 vs 三种终态」；
  常识存疑 = 红旗标记 + 原文 + 两选一 + 编辑修正后入库。
- 结构冲突的小图复用知识图谱区的扁平渲染组件（`structure_preview` 的
  `nodes` / `edges` 字段名与 `GET /knowledge/graph` 一致，可直接喂同一套画布代码）。
- 裁决动作面向教师时不要暴露 `action` 的原文取值，用 `CONTEXT.md` 里的动作名
  （接受新 / 保留旧 / 并存 / 照常入库 / 拒绝 / 编辑修正后入库）。
